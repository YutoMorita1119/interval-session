# 実画面を使う操作チュートリアルの改善計画

## 解決する問題とその理由

現在の「操作と結果を見る」は，参加者関係，縮小版の音配置，簡略化した履歴と結果を3画面で説明している．しかし，実際のゲーム画面，入力欄，待機状態，履歴のピアノロール，結果画面とは構成と操作感が異なるため，一人の閲覧者がこのデモだけを見ても，実システムを操作した感覚や全機能のつながりを十分に把握できない．

実際のゲーム画面と同じUIを，Firestoreへ接続しないローカルの模擬セッションとして動かす．案内は実画面の上へ必要最小限に表示し，閲覧者が音の編集，記録，ターン交代，履歴，再生，最終結果までを短時間で一人で体験できるようにする．

## 成功基準

- 開始画面の「チュートリアル」から，一人用のガイド付き模擬セッションを開始できる．
- チュートリアルでは，実ゲームと同じヘッダー，お題表示，ピアノロール，凡例，再生操作，記録欄，予想欄，履歴，結果画面を使用する．
- 実ゲーム用UIを複製せず，同じ描画処理と主要コンポーネントを再利用する．
- 案内は現在行う操作，その意味，次の操作だけを示し，研究内容を印象付ける宣伝的な説明を加えない．
- 一人の閲覧者が次の機能を一連の流れで確認できる．
  - 2人へ異なるお題が与えられ，7ターン交互に編集する全体構造
  - 自分のお題の表示と非公開範囲
  - 基本和音，自分の音，相手の音の見分け
  - 基本和音と相手の音の削除，空きマスへの音の追加
  - 盤面全体の再生と停止
  - 相手の音の解釈，自分の意図，相手のお題の予想
  - ターン確定後の待機と，相手の応答を受けた盤面更新
  - ターン履歴のピアノロール，音名，度数，記録，再生
  - 7ターン終了後のお題開示，双方の最終予想，一致／不一致
  - 結果から開始画面へ戻る操作
- 操作が必要な段階では対象箇所を明示し，未実施のまま先へ進めない．ただし，閉じる操作は常に可能とする．
- 7ターンすべてを手作業させず，代表的な自分のターンと相手の応答を体験した後，残りは模擬履歴として進め，数分で結果まで到達できる．
- チュートリアル中にセッション文書を作成・読込・更新せず，Firestoreのリスナーも開始しない．
- チュートリアルを終了すると，音声，タイマー，模擬状態，入力値，ダイアログを破棄し，通常の開始画面へ戻る．
- PC表示と360～390px幅の表示，マウス，タッチ，キーボード操作で完了できる．
- 既存の実セッション，Firestore契約，Security Rules，7ターン進行を壊さず，既存テストと追加テストが成功する．

## スコープ

対象は，開始画面の「チュートリアル」導線，チュートリアル状態モデル，実ゲーム画面の再利用，ガイド表示，ローカル模擬ターン，履歴・結果表示，チュートリアル用音声再生，関連するCSS，README，自動テストである．

本番のFirestoreデータ構造，Security Rules，匿名認証方式，実セッションの作成・参加・確定処理，お題6件，音声合成方式，研究データ分析は変更しない．通常プレイできる一人用ゲームも追加しない．

## 制約と依存関係

- チュートリアルは通常ゲームと同じDOMと描画処理を使用し，モードによってデータ供給元だけを切り替える．
- 通常モードはFirebase gateway，チュートリアルモードはブラウザ内の模擬状態を使用する．チュートリアル側からFirebase gatewayの書き込み・購読処理を呼ばない．
- 模擬データは実際のお題を答えとして見せず，「お題A」「お題B」など中立的な表記を基本とする．音や記録の例文も特定の感情へ誘導しすぎない．
- 実ゲーム画面とチュートリアルの分岐を`script.js`だけへ追加し続けず，状態遷移と模擬データ生成はテスト可能なモジュールへ分離する．
- Web Audioはユーザー操作後だけ開始し，画面遷移と終了時に必ず停止する．
- チュートリアル専用の強調表示は操作対象を隠さず，フォーカス移動とスクリーンリーダー向け説明を持たせる．
- GitHubへのpushとFirebase Hostingへのデプロイは，ローカル実装，画面確認，コードレビュー後に改めて承認を得る．

## 実装の順序

1. チュートリアルで扱う機能一覧と状態遷移をテストで固定する．開始，全体説明，お題確認，音編集，再生，記録，確定，待機，相手応答，履歴，結果，終了を一つの状態モデルとして定義する．
2. 通常セッションと模擬セッションが，同じゲーム画面へ必要な状態を渡せる境界を整理する．Firebase固有処理と画面描画の結合を必要な範囲だけ分離する．
3. 現在の3段階チュートリアル専用画面を，実ゲーム画面上のガイド表示へ置き換える．ガイドには進捗，現在の目的，短い説明，閉じる操作を設ける．
4. 実画面で，お題表示，基本和音または相手音の削除，音の追加，再生・停止，3項目の記録，予想選択，ターン確定を順に体験できるようにする．
5. ターン確定後に実際の待機表示を見せ，短いローカル演出の後で相手の模擬応答を盤面と履歴へ反映する．ネットワーク待機とは明確に区別する．
6. 実際の履歴ダイアログを開き，鍵盤，音名，度数，記録，保存盤面の再生を確認する段階を追加する．
7. 残りのターンをローカル模擬データで補完し，実際の結果画面へ遷移する．双方のお題，最終予想，矢印，一致／不一致，最終音再生，履歴，開始画面へ戻る操作を確認できるようにする．
8. 途中終了，再開始，連打，音声再生中の遷移，通常セッションへの復帰を検証し，状態やタイマーが残らないようにする．
9. PC幅と360～390px幅で画面を確認し，キーボードフォーカス，説明文，操作不能時の表示を調整する．
10. 自動テストと構文検査を行い，独立したコードレビューで仕様適合と回帰を確認する．承認後にのみGitHubとFirebase Hostingへ反映する．

## 未解決の質問

- 模擬セッションでは，代表的な2回程度の編集だけを本人に操作させ，残りを自動で結果まで進める方針でよいか．7ターンすべての手操作は理解より負担が大きいため，短縮を推奨する．
- お題は「お題A／お題B」の抽象表記にするか，研究で使う実際のお題を例として1組だけ使用するか．実験参加者への先入観を避けるため，抽象表記を推奨する．
- ガイドの進捗は「1／10」のような段階数を表示するか，「音を編集」「記録」「履歴」「結果」の章だけを表示するか．操作感を損なわない章表示を推奨する．
