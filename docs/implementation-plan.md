# Interval Session 改善計画

## 解決する問題と理由

研究用プロトタイプの通信，手番管理，秘密情報，音声処理が画面内の状態に強く依存しており，2タブでの再現性と安全性が不足している．研究の中心である「表現→解釈→応答」を，一人の閲覧者でも2タブを使って確認できる状態にする．

加えて，開始画面のキャッチコピーや研究背景の説明は，実験参加者に不要な印象や解釈を与える可能性がある．開始画面は操作に必要な情報だけへ絞り，研究内容の説明はGitHubに委ねる．

初回改善では，1和音を4拍へ分割した編集モデル，37音の鍵盤と25行の表示定義の不一致，意味の分かりにくい灰色の初期音，履歴から盤面と音を確認できない回帰が残った．元の研究システムが扱う「4和音＝4配置位置」と，過去ターンを視覚・聴覚で振り返る機能へ戻す必要がある．

その後の確認では，装飾的な字体とカード表現が研究システムよりAI生成UIに見えること，履歴の縮小盤面では音程を判別できないこと，基本和音を残すか削除するか選べないことが分かった．履歴を鍵盤・音名・度数付きの実用的なピアノロールへ改め，基本和音を編集可能な初期配置として復元する．

## 成功基準

- 匿名認証された2タブが，同じFirestoreセッションへ参加できる．
- 7ターンを二重確定せず進行でき，終了時だけ双方のお題と記録を開示する．
- 横方向を4和音に対応する4区画として扱い，各和音へ最大8音を配置できる．
- 37音の鍵盤とピアノロールが全域で崩れず整列する．
- 基本和音は初期状態で灰色の音として表示し，通常の手番では削除できる．削除結果は確定後と再読込後も維持する．
- 削除した基本和音と同じ音を追加し直した場合は，操作した参加者の音として記録する．
- 自分の手番では，自分または相手が追加した音を削除できる．最終ターンでは音を編集できない．
- 自分と相手の追加音は同じ形状とし，色で区別する．
- 元資料の日本語表記「流星群」「氷の結晶」「樹齢を重ねた大木」「ガラスの破片」「猛獣の暴走」「不気味な地下室」を使う．
- 履歴の各ターンに共有盤面と再生・停止操作があり，保存された当該ターンの状態を再生する．
- 履歴の各ターンに左鍵盤，C3～C6の音名，4和音列，所有者色，度数を判別できる約360px高のピアノロールを表示する．
- 全画面を中立的なシステムフォントへ統一し，強い影，過度な角丸，装飾的なカード表現を抑える．
- デスクトップとモバイルで主要操作が利用できる．
- 初回利用者がFirestoreへ書き込まず，音の配置・削除・再生・手番送信を3段階以内で練習できる．
- ゲーム状態，音楽ロジック，音声予定，Firestore契約の自動テストが通る．

## スコープ

Firebase Authentication，Firestore契約とRules，Web Audio，4和音単位のピアノロール，基本和音を含む音の追加・削除，鍵盤と度数付きターン履歴，結果画面，簡素な開始画面，非通信の操作チュートリアル，中立的な字体とレスポンシブUIを対象とする．1人用ゲーム，長い研究説明，Supabase移行，研究データ分析，管理画面は対象外とする．

## 制約と依存関係

既存のFirebaseプロジェクト`musical-comms-app`を使う．外部ライブラリを追加せず，ブラウザのWeb Audio APIとFirebase Web SDKを使う．RulesとHostingの本番反映，実データを使う2タブ試験は，実行直前に承認を得る．

## 実装の順序

1. 基本和音を削除・保存できる音楽モデルと正規化処理をテストで固定する．
2. 各和音の最大8音へ基本和音も含め，すべての配置音を通常の手番で削除可能にする．
3. メイン盤面へ灰色の基本和音と度数を復元する．
4. 履歴を左鍵盤，音名，4和音列，所有者色，度数付きの大型ピアノロールへ変更する．
5. 字体，影，角丸，カード表現を研究システム向けに整理する．
6. チュートリアルとREADMEを更新する．
7. 自動テスト，ローカル画面確認，コードレビューを行う．
8. 承認後にGitHubへpushし，Firebase Hostingへ反映して2タブE2Eを行う．

## 確定した仕様

- 各和音の最大8音には，灰色の基本和音も含める．
- 履歴は約360px高の内部スクロールとし，左鍵盤を固定して音名を確認できるようにする．
- 本番反映後に作成した動作確認用セッションデータは，削除せず保持する．
